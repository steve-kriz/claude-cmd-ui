## Description
Today the Slack bridge uses a single static bot token pasted into `SLACK_TOKEN`
in `.env` (read via `aws.getSlackToken()`), so everyone acts as the same shared
bot. Change this so a user can **sign in with their own Slack login** and the app
uses the token generated by that sign-in.

Implement a full Slack OAuth v2 flow: a "Sign in with Slack" button opens the
system browser to Slack's authorize page; the app runs a temporary localhost
loopback server to catch the redirect, exchanges the authorization code for a
token, persists that token, and uses it for all subsequent Slack calls
(`connect` / `fetch` / `post`). No manual token paste required.

Requires a Slack app configured with `SLACK_CLIENT_ID` and `SLACK_CLIENT_SECRET`
(new `.env` values), with the loopback redirect URL registered as an allowed
redirect URI on the Slack app.

## Acceptance Criteria
- [x] A "Sign in with Slack" button is present in the Slack connect panel (alongside/replacing the manual "Load token" affordance).
- [x] Clicking it opens the **system browser** (via `shell.openExternal`) to Slack's OAuth authorize URL, built from `SLACK_CLIENT_ID`, the required scopes, a `redirect_uri` pointing at the app's local loopback server, and a random `state` value.
- [x] The app starts a temporary `localhost` HTTP server that receives Slack's redirect, validates the returned `state` matches the one it sent (CSRF protection), and renders a human-readable success page in the browser.
- [x] On a valid redirect the app exchanges the `code` for a token via Slack `oauth.v2.access` using `SLACK_CLIENT_ID` + `SLACK_CLIENT_SECRET`, and captures the user's access token (`authed_user.access_token`).
- [x] The obtained token is persisted to `.env` as `SLACK_TOKEN` (via `env-store.set`) and is used by subsequent `slack:connect` / `slack:fetch` / `slack:post` calls with no manual paste.
- [x] If `SLACK_CLIENT_ID` or `SLACK_CLIENT_SECRET` is missing, the UI prompts for and saves them (same pattern as other `.env` secrets) before starting OAuth, with a clear message; OAuth does not start until both are set.
- [x] Failure paths — user denies access, `state` mismatch, token-exchange error, or a Slack `ok:false` response — are surfaced to the user with an actionable message, and leave any previously working token/connection unchanged.
- [x] The loopback server is always closed after the flow completes (success or failure) and does not linger listening.
- [x] `.env.example` documents the new `SLACK_CLIENT_ID` / `SLACK_CLIENT_SECRET` values.

## Cucumber Tests
```gherkin
Feature: Sign in with Slack (OAuth)

  Background:
    Given the Slack app is configured with SLACK_CLIENT_ID and SLACK_CLIENT_SECRET

  Scenario: Starting sign-in opens the Slack authorize page
    Given the Slack tab is open and not connected
    When the user clicks "Sign in with Slack"
    Then the system browser opens Slack's OAuth authorize URL
    And the URL contains the configured client_id, the requested scopes, a redirect_uri to the local loopback server, and a random state

  Scenario: Successful sign-in stores and uses the generated token
    Given the user has started the Slack sign-in flow
    When Slack redirects back to the loopback server with a valid code and the matching state
    And the app exchanges the code with oauth.v2.access and receives a user access token
    Then the token is saved to SLACK_TOKEN in the .env file
    And the loopback server is closed
    And subsequent connect/fetch/post calls use the newly saved token

  Scenario: Missing client credentials block the flow with guidance
    Given SLACK_CLIENT_ID is not configured
    When the user clicks "Sign in with Slack"
    Then no browser window is opened for authorization
    And the user is prompted to provide the client id and secret with a clear message

  Scenario: State mismatch is rejected (CSRF protection)
    Given the user has started the Slack sign-in flow with state "abc123"
    When the loopback server receives a redirect whose state is "wrong"
    Then the code is not exchanged
    And an error is shown to the user
    And any previously working token is left unchanged

  Scenario: User denies access
    Given the user has started the Slack sign-in flow
    When Slack redirects back with an "access_denied" error instead of a code
    Then no token is saved
    And an actionable error message is shown
    And the loopback server is closed

  Scenario: Token exchange failure is surfaced
    Given the user has started the Slack sign-in flow
    When the loopback server receives a valid code and matching state
    But oauth.v2.access responds with ok:false
    Then no token is saved
    And the Slack error is shown to the user
    And the loopback server is closed
```
